# 出库成本、提成差额与界面简化调整

2026-10-19，依据负责人会话中用户四项明确答复。本文记录确认决定及本轮实施范围。应用6024205/0016已实施并完成本轮限定QA/UI、网页链及负责人验收，证据见RELEASE_COST_WORKFLOW_20261020；已部署仍71cf9f6/0015，正式数据切换未执行。UI v2已获用户具体批准，批准证据只维护在UI WORK。

## 已确认决定

1. 毛利及提成改用实际出库时扣减的库存成本金额，替代下单时固定成本的原规则。现场交付按对应实际扣库时点。成本金额为计算依据，展示均价不反向乘回覆盖实际扣减金额。
2. 下单/占货时不显示毛利和提成，只显示所选仓库SKU的当前成本价供参考；此时不形成正式销售成本或正式提成。库存占用、防超卖、修改/取消占货规则继续保留。
3. 历史成本纠错仍正确处理库存及经营成本，但不自动改变已审核提成的当前核定金额。系统计算差额，由老板确认调整，保留原批准与调整记录，不开放自由覆盖提成数字。差额相对当前有效核定金额计算，不能重复扣减。
4. 系统确认调整金额不表示实际补扣资金已完成；资金处理继续线下，沿用既有处理完成记录，不新增支付模块。
5. 销售自行出货权限保持当前实现，不调整账号/角色。不新增临时“补记出货”入口，沿正常订单、收款、发货流程。
6. 界面与日常信息量继续按最小原则收缩；尚未明确取消的客户/收件、凭证、收货完成、到账核对和权限条件不能因简化而删除。

口径解释：快递实际发货/现场交付扣库时即可形成并展示毛利及计算提成；快递确认收货仍是正式计入提成的既有后续条件，不将两者混同。已确认但尚未完成线下补扣的差额记录逐笔保留；新的差额仍只与当前有效核定额比较，不重复叠加旧差额。成本纠错审批与接受提成差额是分别明确的动作，可在同一页面办理，不能自动连带批准。

以上替代此前下单固定单位成本、增量换仓整单重锁成本及采购纠错自动同步修正已审核提成的目标规则。候选服务/API已采用新口径，既存旧单兼容原语义；运行环境需后续发布及迁移才改变行为。

## 实施与发布边界

- 确认新成本口径对历史订单的迁移范围，保留原有效记录，不默认覆写旧订单或将未出库金额填0伪装为确定毛利。
- 已有2026-10-19业务库只读预检指纹显示销售订单/明细、收款、提成核定/差额记录均为0，原业务库只有期初；这只是已核快照，不是假定任意旧库都无订单。后续实际迁移前再核当前状态，测试旧订单与尚未导入的来源历史分别处理，不泛化制造旧真实订单迁移阻断。
- 新单、改单、发货/现场交付、成本回放、运费修改、报表/API/Excel同步校准；未出库只显示当前成本参考，实际出库后才生成对应毛利/提成。
- 已核定提成金额、系统最新计算值、待老板决定的差额必须区分；已确认调整与待处理建议不能混入同一合计。旧建议过期、连续纠错、重复确认及金额版本变化需服务端重新校验。
- 未首次审核的订单仍按正常完成/到账核对/提成审核条件计入，不能因成本纠错或本次调整而提前计入。
- 普通运费更正等此前重审规则不在本次用户明确取消范围；其与纠错差额确认怎样复用由后端给最小方案，不能自行扩大冻结策略。
- 数据重建仍因历史状态/客商等问题暂停，不把这次口径调整当作源数据缺项已确认、导入已完成或云关停条件已满足。

## UI目标及批准范围

| 页面 | 候选简化 | 保留条件 |

## 后端实施边界（2026-10-19启动）

- 复用现有订单金额与库存出库流水，不新建成本账。订单加最小成本口径标识：既存订单保留旧快照语义，新单使用实际出库语义；不批量重算旧单。迁移前实际库状态仍须在后续部署窗口核验，本轮只在隔离合成库验证。
- 新单未实际出库的正式成本、毛利及提成为空；下单/修改/占货只提供当前仓SKU成本参考。出库/现场交付同事务保存实际扣减金额，按收入减实际成本减出库运费计算毛利、按整单毛利10%计算提成，维持三位精度和既有尾差规则。
- 回放、报表/API及Excel同步处理新旧口径；未出库不以零冒充已实现数值。多仓/同仓同SKU重复行须保证明细与库存流水、整单成本对账一致，按既有确定性分摊约定处理，不以展示均价乘回覆盖实际金额。
- 普通运费更正继续原有重审规则；采购纠错生效不自动更新已核提成。老板差额确认独立、服务端算金额，以当前有效核定额为基线，保存原核定与调整记录；重复确认、过期版本和连续纠错须校验。不得把采购纠错审批变成强制附带提成决定的入口。
- 本轮应用范围仅模型/迁移、服务/API、回放、报表导出与必要回归；不重排页面或实施候选UI、不增加日志/依赖、不导真实数据、不更改权限/账号、不改运行环境。API变化及现有页面消费者风险必须交付说明，不把后端通过称全页面可用。
- 自测固定提交后停止应用写入，交QA用隔离PostgreSQL验成本同额、失败回滚、占货、精度、多仓、幂等/过期版本、报表及旧单保留。负责人验收后再安排后续页面与发布，不直接部署。


## 提成差额独立确认合同（2026-10-19收口）

- 成本纠错审批只落实库存及经营成本重算，保留当前核定提成，不自动生成已确认差额，也不等待老板逐单选择。
- 复用纠错 `before_after` 保存当时影响建议快照，复用 `BusinessOperation` 记录独立的调整/保持决定，`CommissionAdjustment` 只保存已确认非零调整；不新增待审表或通用审批模块。
- 独立确认请求包含操作键、来源纠错、订单、订单金额及核定期望版本、调整/保持选择；不接收客户端金额。服务端按最新有效事实计算，相关版本/建议过期则拒绝并要求刷新，成功操作重试按既有幂等返回。
- 调整以当前有效核定额为基线；更新当前核定前保留原核定依据及前后金额记录。保持则记录本次明确决定及计算版本，不自动恢复因普通运费/收款变化而失效的审核资格。旧的已确认但未线下完成调整分别保留，不重复叠入新差额。
- 只允许既有OWNER老板角色或is_superuser管理员执行；普通人员即使同时拥有review_commission和approve_costcorrection也不自动获得此动作，不新增权限/账号配置。项目任务授权不是系统业务权限。此独立操作不转账、不代表线下资金处理完成。
- 具体路由/响应及回归证据由后端固定交付，负责人同步公共API/SPEC；本合同批准不代表已实现或已测试。

独立确认端点合同：`POST /api/v1/orders/{order_id}/commission-adjustment-confirm`（无尾斜杠），请求包含 `operation_key`、`cost_correction_id`、`expected_amount_version`、`expected_approved_amount_version`、`decision`（adjust/keep）。响应须区分决定、现核定/系统计算/差额、版本及非零调整记录，保留既有有效身份与订单可见校验。具体JSON字段由固定后端交付同步API规格。
