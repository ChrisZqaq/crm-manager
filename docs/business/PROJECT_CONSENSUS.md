## 背景与目标

- 经营宝可梦、符文战场、航海王、球星卡、漫威等 TCG，以及手办周边。
- 当前有 3 家门店、3 个仓库，后续仓库数量可增加；4 名销售、1 名仓管兼财务，老板负责合作方调货。
- 年销售流水约 8,000 万元，商品数为几百个，日订单和出货量波动较大。
- 线上以原箱 toB 为主，线下以原盒、原包、周边 toC 为主。
- 当前使用银豹，销售、群消息、个人 Excel、财务 Excel 重复登记，月底重复核对。
- 新系统以统一订单和库存记录为基础，后期可能替代银豹；当前不开发银豹同步。
- 银豹导出仅曾作参考，不作为新系统导入规则。用户按新模板盘点填写；从上线时实际在库数量及成本开始，旧业务、旧订单不导入。
- 2026-10-03确认：正式上线安排暂停各仓实际出入库的盘点切换窗口，用户确保期初数据准确并对齐同一切换时点，正式导入核对后恢复业务；不开发旧系统同步或期间自动追差。开发测试使用合成数据，少量模板样例可辅助验证但不作正式库存。
- 正式期初涵盖所有仓库、一次整批确认入账；确认前可反复校验预览，成功后关闭库存导入口，拒绝重复、覆盖或追加。测试库试导与正式库存隔离，期初错误核对纠错而不重传覆盖，上线后采购走正常入库。
- 已确认期初录错复用采购纠错规则：无后续影响仓管修正对应期初记录；有影响仓管提交变化预览、老板确认后整体重算库存、订单成本及提成。保留前后值、原因和必要审批、非负校验，不重导、不增加独立审批、不改为采购单。

## 产品形态

- 技术栈已确认采用 Django＋PostgreSQL。按用户2026-10-03最新指令，先整理并确认完整PRD、SPEC和数据库设计，再开始开发；见 [文档索引](../README.md)。设计草案中的建议不自动成为业务共识。
- 网页操作，对外提供业务 API；后续小程序复用同一套业务规则。
- 使用场景已明确：当前人员主要在同一门店及仓库工作，同时远程操作另一仓库出货，外出时需手机或电脑访问同一系统。用户已有上海轻量服务器：Ubuntu24.04、2核2GB内存、50GB磁盘（剩余约27GB），运行Hermes Agent，有可用域名。作为部署候选，实际负载及资源余量仍待验证；后续小程序复用同一后端和业务API，不建立第二套库存账。
- 已确认备份恢复目标：故障时最多丢失1小时新增数据。每30分钟备份数据库及新增、变更的凭证文件，保留最近24小时的半小时备份、最近7天每天一份，服务器之外保存副本。上线前实际恢复并核对库存、订单与截图一致性；复用定时任务和备份工具，不做主从或高可用集群。外部存放位置及具体执行方案仍待确认和验证，当前未部署备份。
- 用户提供老板家中NAS作为异地备份候选；用户明确将品牌型号、持续开机、可用空间及服务器连接方式核对列为上线前待办，当前不要求提供，不阻碍文档讨论及后续本地开发。上线前仍须验证半小时备份及1小时恢复点目标。
- 各销售渠道共用库存池，但实际库存按仓库分别管理。
- 销售人员与销售渠道分别记录，一张订单属于一个销售，无多人分佣。
- 第一版以功能和数据正确性为核心，不开发复杂界面或完整 ERP。
- 第一版支持账号密码登录；销售、仓管／财务、老板按角色配置业务权限开关，账号可兼任、权限取并集，不做个人覆盖。老板和管理员管理普通角色，固定超级管理员不受开关限制，只有管理员能授予或撤销管理员身份。不做注册、短信验证码、复杂权限规则引擎或多级审批，详见 [登录与权限](ACCESS_CONTROL.md)。
- 商品信息包括成本对所有人员一致；客户、订单及提成默认本人范围，额外设查看全部开关。销售兼任仓管获得仓管全部权限。
- 2026-10-03确认各角色初始权限矩阵，见 [登录与权限](ACCESS_CONTROL.md)。仓管／财务默认查看全部订单和提成，但不查看全部客户；老板默认查看全部，销售默认本人范围。对公由财务核对，老板兼任财务可核对对公；私账仍由老板核对。
- 老板亲自提交采购纠错或盘点调整时可自行确认，保留记录。管理员不绕过库存、金额、凭证等业务校验；权限变化留最小记录。
- 普通人员取得审批权限后，仍不能确认自己提交的采购／期初纠错或盘点；后端检查提交人与确认人，不因权限开关开启而放行。

- 收款核对表展示待核对、待处理、登记金额、订单金额及差额。
- 提成表展示预估、待复核、已计入及纠错差额。

## 采购、库存与成本

- 采购入库细则见 [采购入库](PURCHASE_RECEIVING.md)。系统从实际到货入库开始管理，需求收集、订货、提前收款和分配在线下完成。
- 一张入库单限定一个供应商、一个仓库。供应商名称必填；送货单照片或第三方截图选填。人工填写 SKU、实收数量、实际进价及运费，确认入库前必须有采购价。
- 2026-10-03确认：入库确认前统一展示仓库、供应商及明细SKU、单位、数量、采购单价、分摊运费和成本金额，由人员核对后确认；替代此前自动数额过大提醒，不增加异常阈值配置或历史价格比较，数量、金额、必填成本及受限超量硬校验仍保留。
- 官方及合作方调货统一走采购入库。物流站点也可作为仓库，实际到货清点后入库、转寄后销售出库，不开发独立转寄分支。
- 入库运费默认 0，人工填写各明细分摊金额，计入商品库存成本。不另做运费付款管理。
- 已确认真实零采购价允许入库，确认摘要提示核对；价格为空仍不能确认，不自动按0处理，有运费照常计入成本。不增加赠品采购模块或额外审批。
- 每个仓库、每个 SKU 独立采用移动加权平均成本。
- 入库后的平均成本 =（原剩余库存成本金额 + 本次入库成本金额）/ 入库后的数量；锁定和占用的在库货物仍属于剩余库存。
- 新单正式提交只占货并显示当前成本参考，正式成本／毛利／提成在实际出库产生；已出库后普通采购不回改该单。既存旧单仍保留旧快照语义。
- 2026-10-19替代原下单快照规则：新订单毛利和提成与实际发货／现场交付库存扣减同成本口径，报表区分新旧口径。
- 库存尾差：每次按当前剩余成本金额÷剩余数量×出库数量计算并保存3位；清空时扣完剩余成本，数量成本同时归零。新单使用实际扣减金额，不用展示均价乘回覆盖。
- 新单按仓库SKU实际扣减成本分摊明细，末行承接尾差；既存旧单仍保留原3位单位快照及其舍入差异，不批量迁移历史金额。
- 实际库存、订单占用、客户预留、囤货锁定和破损待处理数量分别管理：可售数量 = 在库数量 - 订单占用 - 客户预留 - 囤货锁定 - 破损待处理数量，不重复扣减。
- 销售正式提交订单检查并占货，未付款也可占货。到货可同时预留客户数量，销售线下联系仓管解锁需要的数量为公共可售库存，再正常下单。
- 暂不保护解锁数量不被其他销售使用，不做指定订单放行或预留来源追踪；防超卖与重复提交校验仍保留。
- 所有未发货订单取消统一释放订单占用、恢复可售，需要继续预留时由仓管人工锁回，不自动退回预留。不做自动到期释放。
- 破损货登记并保留采购成本，但不可售；仓管线下换货或退款后记录实际库存处理，不删除历史入库。换货不增加总成本。
- 2026-10-03确认：破损退款处理时减少对应在库及破损数量，按当时移动平均成本扣库存，清空时扣完剩余成本；实际退款与扣减成本及差额分别记录，不摊其他商品，不重算历史订单及提成。此前“少买一箱”明确为当时减少库存，不回溯修改原采购；原单确实录错才走采购纠错。退款后残留实物在线下处置，不恢复可售。
- 破损退款未退还的采购运费记录为本次采购损失，不摊给其他商品，也不影响其他订单提成。
- 囤货由仓管或老板锁定、解锁，记录原因。
- 禁止超卖；并发提交必须原子完成可售数量检查与占用，重复请求不得重复占货或扣库存。
- 发货时减少实际库存，同时释放对应订单占用，不能重复扣减可售数量。
- 库存不允许直接改成任意数字，每次变化通过有关联单据的库存流水解释。
- 2026-10-03确认低库存提醒：后台维护单一全局默认阈值，不区分单位和仓库；入库明细可填SKU专用阈值，留空使用默认，另有关闭该SKU提醒按钮。SKU专用值及关闭状态各仓共用，各仓按自己的可售数量≤有效阈值判断；页面标记及筛选，无IM、短信、邮件或定时任务。阈值为非负整数，0表示售罄提醒，初始默认值为5，后台提供全局开关；关闭后全部SKU不提醒但保留配置，重新开启恢复按原配置判断。
- 入出库、赠送、盘点纠错等应保留原因和对应凭证；基础单据与库存流水不等同于后续操作历史审计。
- 第一版不做保持SKU不变的独立仓库间调拨；同仓或跨仓拆箱包含在本版。货物无需拆箱时，仍可直接选择所在仓库向客户出库。

## 拆箱与赠送

- 拆箱和赠送均由仓管登记，暂不增加单独审批流程。
- 一张拆箱单同时减少来源 SKU 库存、增加目标 SKU 库存，避免分开操作漏记。
- 2026-10-03最新确认：门店作为独立仓库管理实物，同时销售订单可选择门店零售渠道，库存位置与销售渠道分别记录。每张拆箱单选择来源仓库及目标仓库，允许同仓或跨仓，一个来源SKU转一个目标SKU；替代此前仅限同仓的规则。数量人工填写，来源扣减成本全部转给目标；不同转换分别录单，不做一单多个目标商品或独立调拨模块。
- 数量人工填写，不维护自动换算规则；来源成本转移到目标商品，目标商品入库后参与对应仓库的移动平均。
- 示例：总仓1箱成本1,000元，实际拿到门店拆成20盒，仓管一次登记，总仓减少1箱及1,000元成本、门店增加20盒及1,000元成本；门店无原有盒装库存时每盒成本50元，有原库存时参与门店该SKU移动平均。两端变化同事务成功或失败。
- 拆箱属于库存转换，不作为销售渠道或销售收入。
- 活动赠送另行记录赠送出库原因，不产生虚假销售额或提成。门店从门店仓库销售或赠送；赠送卡包时，有包库存直接赠送，只有盒库存先登记盒拆包，再登记赠送，不自动换算。

## 盘点

- 每月由仓管盘点，按仓库和 SKU 核对实际数量与系统在库数量，不能用可售数量代替在库数量进行实物核对。
- 发现差异由仓管提交，老板确认后通过盘点调整单更新库存；确认前原有效库存不变，保留差异和调整原因。
- 2026-10-03确认：盘点至审批期间有关仓库SKU在库数量发生变化，暂停该项审批，仓管重新核对实际数量、更新差异后提交；仅重核受影响商品，不自动推算期间变化。仅占货／解锁不要求重盘，但仍校验当前受限数量；成本变化刷新金额影响，由老板确认。
- 盘点不能直接覆盖库存余额，也不绕过非负库存及受限数量的基础校验；具体操作与并发校验方式在设计时明确。
- 先查差异原因：漏录或错录时修正原业务单据，沿用原单纠错及审批规则，不再用盘点调整重复处理同一差异。
- 确实无法追溯的盘盈、盘亏，按该仓库＋SKU 当前平均成本调整数量及库存成本金额。
- 零库存或缺成本时，由仓管填写调整单位成本、老板确认后生效，不以缺失成本默认为零。
- 2026-10-03确认：盘亏或采购数量纠错使库存不足覆盖占用／锁定时，展示缺口及相关记录，先由人员用现有订单修改取消、预留／囤货解锁操作处理，再由老板审批库存调整。审批时再次校验，不自动分配、不增加一键联动；破损仍按破损处理规则操作。

## 销售、收款与交付

- 详细操作及进入下一步的条件见 [销售履约](SALES_FULFILLMENT.md)。
- 销售人工填写成交单价，选择客户或散客、渠道、商品数量、仓库与交付信息。
- 一张订单支持多个 SKU，销售手动选择供货仓库及数量，正式提交检查并占货、显示当前成本参考；库存不足明确提示。一张订单可从多个仓库出货。
- 未发货修改同步调整占货和订单金额，涉及已收款金额不符时提醒人工处理；已发货不直接修改商品、数量和供货仓库。
- 仅减量释放相应占货、保留剩余原成本；增加数量、换 SKU 或换仓库时整单原子重新占货、按当前成本计算，修改前展示成本及提成变化。改成交价保留成本；改金额、收款账户或截图使原收款核对失效；影响已复核提成的数据修改使老板复核失效。地址和备注不影响上述计算与核对。
- 暂不支持分批发货；一次确认整单发货，支持多个物流单号。
- 快递流程：待确认（已占货）→ 上传收款截图并确认付款 → 待出库 → 填写物流信息并确认发货 → 待收货 → 销售确认收货 → 已完成。
- 未上传收款凭证不能进入待出库；没有确认收货不能完成快递订单。
- 门店现场交付无需物流单号；满足收款凭证要求后，确认交付即可完成。
- 多个银行、微信、支付宝及私人收款账户作为可选择的收款账户记录。
- 每单关联收款账户、金额和截图。暂不支持一笔付款对应多单或一单分多次付款。
- 收款截图必填，收款时间选填；登记金额与订单金额不一致时提醒并要求填写原因，确认后允许发货，不自动视为核对通过。
- 凭证第一版仅图片（JPEG、PNG、WebP），单张最多10MB，一单可多张；收款至少一张、入库仍选填，不支持PDF、OCR、自动压缩或独立文件管理模块。访问遵守对应单据权限。
- 上传凭证后允许销售自行出库，财务后置人工核对；履约状态与财务核对状态分别记录。
- 对公转账由财务核对，老板私账由老板直接核实到账，不由财务重复确认到账。核对发现问题标记待处理并填写原因，未发货暂停出库，已发货保持原履约状态。
- 承运方支持跨越、顺丰、货拉拉；跨越和顺丰用运单号，货拉拉用平台订单号，分别关联订单出货仓库。
- 截图上传不等于财务确认到账，暂不自动识别金额或自动审核。
- 已收款但未发货的取消订单释放订单占用、恢复可售，并保留原收款凭证；不自动视为退款，退款暂时人工记录。
- 出库运费默认 0，人工分摊，扣本单毛利，不改变仓库剩余商品成本。
- 已确认：下单运费默认0，发货／现场交付时填已知值并重算毛利与预估提成；未知不阻止出货，可后续补填。运费修改不改商品及剩余库存成本，已复核提成需老板重新复核，线下补扣仍人工处理，不增加运费支付管理。

## 提成与纠错

- 2026-10-03确认历史报表最小方案：已计入提成因后补运费等普通修改需重审时，保留原计入日期及最后批准金额，新金额单独标记待核对／复核；重新通过后才更新正式金额，保存前后值、差额及确认日期。原期间重新查询显示修正值，已有Excel不自动改写；差额用于解释及线下补扣，不再叠加到修正后的汇总。不增加月度封账或报表快照。未曾计入的订单仍须满足三条件才能首次计入。
- 历史纠错涉及已确认盘点时，保留当时实盘数量及原成本计价依据，重新计算盘点差量并列入老板确认的影响预览，不机械重放旧差量。例：原入库100、实盘95、原差量-5；入库纠正为90后，盘点差量改为+5，盘点后的数量仍为95；历史非负等基础校验仍适用。
- 已确认历史占货区分：已取消或减量且从未造成实际负库存的旧占货，不因纠错后曾超量而重新否定；当前占用及锁定必须合法，历史实际出入库不能为负。原入库100、占80后取消，纠正入库60可通过；实际曾出库80则拒绝。
- 历史纠错使盘点时无均价来源且需要盘盈成本时，暂停纠错，由仓管补填该次历史盘点单位成本并由老板确认后重算；不使用今天成本、不默认为0。

- 整单毛利 = 明细成交金额合计 - 明细成本金额合计 - 本单销售出库运费；提成 = 整单毛利 × 10%，最后四舍五入保存到 3 位，不逐条舍入提成后相加，运费不能重复计入成本。
- 新单正式提交只占货，不预计算毛利提成；实际出库后才形成计算值，正式计入仍须订单完成、到账核对及老板复核。
- 未实际出库的新单正式成本保持空值，不以 0 代替，不产生虚假提成。采购入库缺价格不能确认，不支持缺采购价正式入库后再发货。
- 完成订单、对应账户收款核对通过、老板提成复核通过后正式计入提成；对公由财务核对，老板私账由老板直接核对。
- 亏本订单允许负提成；退货不扣提成。
- 当前允许人工纠正成本、凭证与已计入提成等信息；采购纠错未影响后续业务时可修改并重算，已影响后续业务时由仓管提交、老板确认，重算受影响库存成本及订单提成，包括已审核提成。
- 2026-10-19替代：采购纠错批准保留原核定提成，老板／超级管理员另行确认系统差额或保持核定额。保留原批准与决定、差额及线下完成记录；未核定仍正常审核，不自动计入。
- 纠错影响未发货占货时，先通过已有订单修改／取消及锁定解锁操作人工处理，再审批库存调整，不做独立联动修改模式。已实际发放提成展示前后金额和差额，在线下补扣，销售自行标记完成，系统后续以纠正值为依据并保留对比记录。
- 采购纠错及重算不能造成当前或受影响历史时点负库存；出现矛盾时阻止修改生效、保留原数据并提示核对单据，不增加专门的异常处理流程。
- 自动成本更新与人工纠错必须区分：采购入库不能重算历史订单，明确的人工纠错可以更新。
- 2026-10-03确认：采购纠错按业务在系统中实际生效的先后顺序重算，不按人工填写的单据日期重新排序；沿拆箱等实际成本流转关系传播，后续采购不倒算到此前订单下单时点。
- 库存纠错仍需通过业务单据完成。保留采购纠错原因、前后值、提交人、确认人、时间等最小审批记录；完整操作留痕审计暂不开发。
