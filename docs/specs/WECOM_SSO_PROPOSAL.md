## 最小技术合同

| 项目 | 做法 |
| --- | --- |
| 入口 | 企微应用主页设为同HTTPS域/accounts/wecom/login/?next=/（根/仍保留原密码入口）；新增固定HTTPS回调GET /accounts/wecom/callback/。保留/accounts/login/，不全局替换LOGIN_URL。回调可写认证session，不写库存/业务单据，不将其误称纯只读请求。 |
| OAuth | 服务端生成随机state，绑定当前session、五分钟内一次使用，并验证安全站内next；通过官方gettoken及auth/getuserinfo换取企业成员userid。state/code/token/Secret不进前端结果、业务或代理查询日志。 |
| 绑定 | 现AccountProfile加可空唯一wecom_userid；绑定已有用户时按需补profile。管理员沿现后台显式绑定，不增公开自助绑定/自动创号/授角。字段长度实施前按官方userid约束冻结。 |
| 授权 | 只允许显式绑定获准试点且is_active的User，沿ModelBackend登录和现权限。非成员openid/external_userid、未绑定/重复绑定/停用拒绝。企微应用可见范围不是CRM登录白名单。 |
| 已登录不同账号 | 若当前session的CRM账号与OAuth映射账号不同，拒绝静默切换，提示显式登出后重试；同账号可继续。此为防串号技术默认，不新增身份切换平台。 |
| 缓存 | 复用Django cache，按expires_in留余量缓存token，不新增Redis。当前每进程LocMemCache，初期单worker可用；若实际部署多worker，按真实获取频率再判断，不预建共享缓存。 |
| 错误/退出 | 中文提示，失败不半登录、不自动授权。登出仍走原安全流程。CRM停用应在既有session下一受保护请求生效，并用测试验证；首期由管理员同步停用离职者，不声称企微离职自动撤销CRM session。 |

CorpID、AgentID和Secret在实施获批后的受控配置环节由管理员配置；不在聊天、普通文档或Git索取/保存秘密。官方来源与平台限制见[研究报告](../workspaces/deploy/WECOM-SELFBUILT-RESEARCH-1020.md)。
