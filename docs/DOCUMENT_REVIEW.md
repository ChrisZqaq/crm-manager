## 公式核验

金额使用十进制，保存3位，半值远离零。库存平均计算保留高精度，订单单位成本按已确认规则先固定3位，两者不能混用。

| 场景 | 应有结果 |
| --- | --- |
| 入库60、预留50；解锁20后下单20 | 初始可售10；解锁后30；下单后占用20、预留30、可售10 |
| 10箱成本1,000，下单5箱，再入库10箱成本2,000，随后发货5箱 | 订单成本500不变；库存扣750；剩15箱、成本2,250 |
| 3件总成本1.000，逐件出库 | 库存依次扣0.333、0.334、0.333，清空后成本0 |
| 同上，正式下单3件 | 单位成本快照0.333，订单成本0.999；实际库存清空扣1.000，差额不改提成 |
| 两行毛利各0.005 | 整单毛利0.010，提成0.001，不是逐行舍入后的0.002 |
| 正负半值 | 1.2345→1.235，-1.2345→-1.235 |
| 原10箱单价100纠正为110，下单5箱后再入库10箱单价200，再发货5箱 | 重算订单成本550；发货前成本3,100；库存扣775；剩成本2,325 |
| 20箱成本3,000，其中1箱破损，供应商退款100 | 按当前均价扣150；剩19箱成本2,850；扣减成本减退款为50，单独对比 |
| 总仓1箱成本1,000转门店20盒，门店原无该盒库存 | 总仓该箱SKU清空；门店20盒成本1,000、均价50，两端同时生效 |
| 同一转换，门店原有5盒成本200 | 门店25盒成本1,200、均价48，不覆盖成全部50 |

上述10组数字用精确十进制重新计算通过，只验证文档样例，不替代未来数据库、并发、权限及回滚测试。

退款差额固定说明为“库存扣减成本－实际退款金额”，可以为负；未退采购运费是说明项，若已包含在上述差额中不能再相加。报表毛利使用下单成本，不能命名为完整财务利润。不同单位数量不直接加总。

## 总审前必须补齐的技术设计

1. **最小历史输入与有效成本版本。** 保留订单提交、仅减量沿用成本、整单重新固定成本等必要业务输入，普通覆盖当前订单字段不够。明确纠错后的有效流水如何与旧金额记录区分，避免重算时重复累计或丢失原审批对比。复用业务记录与必要快照，不记录所有页面操作。
2. **实际生效顺序及锁定方案。** 不能只靠创建时间或自增ID宣称是实际生效顺序；固定锁顺序须兼顾订单、余额、跨仓成本链和纠错，避免审批时漏掉目标仓库的新业务或出现死锁。初版可选择更保守的串行处理方案，但不引入消息队列或分布式锁；选定后用PostgreSQL验证。
3. **库存一致性。** 余额中的占用、预留、囤货、破损须与有效订单、锁定记录、破损记录一致，所有更新走同一事务。数量0时库存成本0；有货而均价确为0合法，不能把真实零成本视为缺成本。平均成本在无货时显示无值，不能除以0。
4. **金额与核对版本。** 分别明确应收／凭证版本、提成金额版本及库存数量版本；不为所有字段建立独立版本。明确运费后补和收款修改导致旧核对／复核失效时，已计入记录和差额如何展示。
5. **最小可实施接口。** 当前SPEC只列资源与查询含义，尚无完整路径、请求、响应及错误合同；数据库仍缺部分字段、约束和索引细节。需要整理以供总审，不把每个技术参数都变成用户问答，也不宣称已经冻结。

这些属于实现现有规则所需的技术工作，无须新增业务模块；未经开发基线批准只完善文档。

## 补充复核：历史报表与纠错的最小方案（待总审）

已确认历史报表继续查询现有业务数据，不新增月度封账表或保存每次报表快照。已计入提成后补运费等普通修改时，保留原计入日期及最后批准金额，新计算值单独标记待复核；重新核对／复核通过后才更新正式金额，并保留原值、新值、差额及确认日期。原日期下重新查询会显示修正值，已导出的文件不自动改写。差额仅作为解释清单，不再叠加到已经采用修正金额的汇总上，避免重复计算；这是动态修正报表，不冻结历史月份，用户已确认。

销售数量、成交金额、发货日期和订单履约事实不因采购成本纠错而变化；关联毛利可能随纠错更新。老板审批采购纠错仍按已确认例外同时批准原已审核提成的新金额。普通运费修改则必须重新复核，不能冒用采购纠错例外。

历史纠错进一步发现的必要边界：

- **盘点实盘数与调整差量必须区分。** 例：原入库100，实盘95，原盘点差量-5；若原入库纠正为90，机械重放-5会得到85，不能代表曾确认的实盘95。已确认保持盘点的实际观测数量95，重算当时差量为+5并在纠错预览中展示；已确认盘点不得变成无提示的成本吸收项。盘点成本原采用移动平均还是人工输入也须保留，不能重算时任意替换。该业务规则已确认，具体算法及验收仍须总审。
- **只改变解释与计算，不重发真实动作。** 回放发货、退款、换货、拆箱和锁定事件是在临时计算状态中重建结果，不再次扣有效库存、不发送物流、不执行资金操作、不创建第二笔实际收款。批准后一次替换有效计算结果，重复审批不再次应用。
- **多次纠错必须以当前已批准版本为起点。** 第二次纠错不能恢复第一次纠错前的价格或成本；差额相对于上一次已批准金额计算，已经完成的补扣记录保留，不覆盖成一次总差额。
- **库存量合法不代表历史成交可重建。** 改采购SKU、仓库、数量时，实际已发货订单与拆箱来源仍固定，历史某时点无货或出现负库存必须拒绝；不自动替换销售商品，不凭纠错改写发货事实。
- **影响预览必须分开列出。** 原采购／期初变化、库存数量成本、拆箱承接成本、订单下单成本、实际库存出库成本及提成分别展示；采购纠错不因成本变化自动使客户到账核对失效。

用户已接受最小执行设计方向：用PostgreSQL的一把事务锁协调库存及成本相关写操作，先取得该锁再按统一顺序访问订单和余额；普通查询不阻塞，预览不长期持锁，批准时核对预览依赖后在一个事务内完成重算及写回。第一版优先简单串行化，暂不设计跨仓分布式锁或后台队列；长历史重算的等待时间须用实际数据量验证，不能在2核2GB服务器上未经测量承诺性能。
