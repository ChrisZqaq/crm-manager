## 上下文与问题记录

阶段进展集中在DEVELOPMENT_PLAN.md，问题集中在 [问题记录](ISSUE_LOG.md)，业务决策在对应共识及PRD／SPEC。每次阶段交付和审查结论及时写回，不等待会话结束；只读审查结果由负责人归档，开发者不能用聊天声明替代记录。

每个阶段记录状态、负责会话、交付版本、验收证据、阻断问题ID及下一步。未明确的规则标记待确认并报告负责人，不自行以默认值或临时补丁继续；负责人需要业务决定时询问用户，非依赖工作可继续。发现临时方案须说明影响及关闭条件，不能沉淀未经批准的技术债。

交接顺序：原负责人先核对并保存基线状态、活动会话ID、当前阶段和版本、未决问题及精确下一动作；创建一个接任会话并让其读取文件、复述待办与边界；确认交接后更新会话登记，向其余角色告知唯一接任负责人，再让原会话停止接单。角色替换同样先固定交付，禁止旧新角色同时写入或同时派发任务。不按固定token数机械切换，不同时更换三个会话。

## 阶段循环

1. 用户确认开发基线后，负责人依据 [开发计划](DEVELOPMENT_PLAN.md) 派发一个阶段，明确范围、排除项、验收场景及交付要求。
2. 开发者只实现本阶段并自测，交付明确版本；消息给测试后停止修改应用文件，等待负责人。
3. 测试者先确认版本，再执行独立测试并向负责人发送自包含报告；通过与失败都报告，不自动启动下一阶段。
4. 负责人检查代码、测试命令及实际结果。失败或未满足验收则派发修复；通过后更新阶段进度，再派发下一阶段。

所有会话当前复用同一项目目录，不并行修改同一批文件；开发阶段负责人主要读代码，独立测试阶段开发者停止写入。测试若需要补充测试文件，由阶段任务明确授权，不自行修改业务实现。发现版本变化重新明确交付，不对混合版本声称测试通过。

## 阶段任务与交付格式

阶段任务至少包含：已批准基线、阶段编号和目标、允许修改范围、验收结果、必要测试、交付版本及交接对象。不会只给“完成这个模块”这种缺少边界的指令。

开发交付至少包含：实现范围、文件或提交版本、运行方法、自测命令及真实结果、已知限制。测试报告至少包含：被测版本、实际命令和结果、失败复现、未测项及限制、通过／不通过判断。不能只凭“测试通过”四字推进。

进度以负责人审查后的记录为准，不以开发者完成声明为准；阶段记录集中维护在开发计划中，详细证据按需链接，不为每次消息创建文档或维护多份进度账。

## 边界

- 此协作安排不是开发基线批准。当前由负责人补齐可实施数据库、历史重算算法、事务及API合同后提交用户总审。
- 最小实现、业务未知规则先明确、必要日志批准及真实PostgreSQL并发验证仍按AGENTS.md和SPEC执行。
- 未经用户明确请求，不推送GitHub、部署或连接真实生产服务；不提交真实客户资料或凭证。
- 消息交接可以触发后续会话，但不保证在应用不可用、会话出错或额度不足时持续运行；恢复时从最后审查通过的阶段及明确交付版本继续，不跳过验证。
