# 采购入库模块共识

本文件记录采购入库讨论形成的业务共识。具体数据库、接口和重算算法尚未设计；文末列出的未定事项不得自行推定。

## 范围与流程

- 系统从实际到货、清点入库开始管理。
- 客户需求收集、官方订货、第三方调货协商、提前收款及到货数量分配在线下完成，不建立未到货订单、采购订单、需求配额或自动配货系统。
- 销售按线下最终分配的数量在系统下单，关联实际收款凭证；系统不负责计算原需求不足产生的退款。
- 官方进价由官方确定，第三方进价由老板提供；通常由仓管兼财务清点、录入。
- 流程：实际到货 → 清点 → 填写入库单 → 确认入库 → 更新库存及成本，同时处理本次预留和破损数量。

## 单据内容

| 范围 | 信息与约束 |
| --- | --- |
| 单据 | 一个供应商、一个仓库；供应商名称必须记录 |
| 明细 | SKU、实收数量、采购单价、分摊采购运费、客户预留数量、破损待处理数量 |
| 凭证 | 选填，建议提供官方送货单照片或第三方渠道截图、付款截图 |
| 运费 | 默认 0，人工分摊到明细，计入商品库存成本，不管理采购运费是否付款 |
| 采购价 | 确认入库前必须填齐，不能用缺失值或默认零代替未录入的价格 |

- 数量必须为正整数，采购单价和运费不能为负；各受限数量不得超过适用的实收正常数量。
- 真正的零采购价与未填价格必须区分，其具体允许场景在字段设计时明确。
- 对疑似过大数量或金额提醒确认，不任意设置硬上限；提醒阈值待确认。
- 同一入库单多仓到货时，分别录单，不增加单内跨仓拆分功能。
- 供应商档案形式、单据日期、编号和具体字段类型在数据库设计阶段确定。

## 仓库与物流站点

- 仓库维护名称和地址，入库时选择。
- 物流站点可作为仓库，例如“上海物流站点”；确认实际到货和数量后正常入库，转寄后正常销售出库。
- 物流站点货物由仓管及相关销售共同核实实收数量、采购价，能提供送货单及客户物流单号。
- 不增加单独的转寄业务系统，不因供应商通知已发货就增加实际库存。

## 库存与移动平均成本

- 官方、第三方及物流站点统一使用同一种成本规则。
- 每个仓库＋SKU 独立计算移动加权平均成本。
- 本次入库成本金额 = 实收数量 × 采购单价 + 分摊采购运费。
- 入库后平均成本 =（原剩余库存成本金额 + 本次入库成本金额）/ 入库后在库数量。
- 客户预留、订单占用、囤货和已购入的破损货均属于在库库存并保留成本；破损货不可售。
- 可售数量 = 在库数量 - 订单占用 - 客户预留 - 囤货锁定 - 破损待处理数量；这些受限数量不得重复扣减同一件货。
- 正常且未锁定的货在入库确认后立即可售。
- 库存和成本更新必须一起成功或一起失败，重复确认不得重复入库。
- 后续普通采购入库不自动修改已固定的历史订单成本；明确批准的采购纠错是例外。

## 客户预留与订单放行

- 入库时可以人工填写客户预留数量，不记录线下的原始需求或自动比例分配。
- 示例：实收正常货 60 箱，预留 50 箱；确认后在库 60、客户预留 50、可售 10。
- 入库和预留一次完成，不能先让全部货物可售再补锁定。
- 客户预留与主动囤货区分原因；不建立独立的销售配额系统。
- 销售按线下分到的数量填写订单，仓管针对指定订单放行。
- 放行时一次完成“客户预留减少、对应订单占用增加”，不先释放到公共可售库存。
- 放行时按各供货仓库当前平均成本固定订单成本，并预计算提成；待放行时不能当作已经占货或固定成本。
- 普通现货订单在下单占货时固定成本，不需要预留放行流程。
- 未发货取消：来自客户预留的订单数量退回客户预留；普通现货订单数量恢复可售。不做自动到期释放。
- 一张订单混合预留及普通可售来源的具体操作尚未确定，不能自行假设。

## 破损与换货退款

- 清点时登记破损待处理数量，不分配、不销售，保留采购成本。
- 仓管在线下完成换货或退款；第一版不做完整售后申请和物流跟踪。
- 正常替换货实际到达并确认后，记录处理结果，恢复对应正常可售数量，不能重复增加数量或总成本。
- 破损退款按减少对应采购数量及成本处理，相当于少采购对应数量，不直接删除历史入库记录。
- 退款后即使破损实物留在公司，也不纳入本系统管理库存，不恢复可售；其后续使用或处置在线下完成。
- 退款金额及采购运费退还范围如何影响成本，在成本设计时明确；不能默认所有费用均已退回。

## 入库纠错与审批

- 未影响后续业务的错误允许修改，修改后统一调整相关库存和成本。
- 已影响后续业务的错误，由仓管提交、老板确认后生效；待审批期间原数据继续有效，拒绝不改变原数据。
- 确认前展示受影响的库存、订单成本和提成变化。影响范围包括成本流经拆箱、调拨等业务后的关联数据，不能只重算当前仓库余额。
- 采购纠错可以重算受影响的库存成本和订单提成，包括已审核、已计入的提成。
- 对已实际发放提成，展示修改前、修改后和差额；补发或扣回在线下执行，销售完成后自行点击完成。本系统不执行资金转移，完成后以纠正数值作为后续依据，保留差额对比及完成记录。
- 审批及执行时必须保证确认的修改内容和影响结果仍然有效；并发操作不能造成部分更新或未经确认的结果生效，具体实现待设计。
- 重算必须完整成功或完整失败，失败时保持原有效数据并明确反馈。
- 最小审批记录保留纠错原因、前后值、提交人、确认人、时间和结果；这不扩展为完整操作历史审计。
- 基础校验不能因老板确认而跳过。数量修改影响未发货订单占用时，可进入修改模式调整相关占货数量，必须同步核对订单数量，不能只改库存计数。
- 纠错及重算后库存不能为负；若导致当前余额或受影响历史时点出现负库存，阻止修改生效，提示核对相关入出库单据，保持原数据有效。不增加专门的异常处理流程。

## 最简单的登录和身份区分

- 第一版使用账号密码登录和后端角色权限，替代此前“暂不做鉴权”的原型设想。
- 最小角色方向：销售、仓管／财务、老板；账号可以兼任，销售需要出货权限时可兼任仓管。
- 老板负责受影响采购纠错确认，不能仅靠同一个人连续点击两个确认框代替审批。
- 优先复用框架现成登录与安全密码存储，不做注册、短信验证码、复杂权限配置和多级审批。
- 最终权限矩阵、账号初始化方式及自我审批限制尚待权限模块确认。
- 新增或调整诊断日志、埋点仍需事先与用户确认，遵循 [协作规则](../AGENTS.md)。

## 最小验收场景

1. 普通到货入库，含人工分摊运费，库存及移动平均成本正确。
2. 入库 60、预留 50，可售 10；仓管给指定订单放行 24 后，预留 26、订单占用 24、可售仍为 10。
3. 多个销售并发占货不超卖，重复确认不重复入库、占货或扣库存。
4. 预留订单取消退回预留，普通订单取消恢复可售。
5. 破损货计成本但不可售，换货不重复增加库存或成本。
6. 未填价格、负数、数量不合法及超量预留不能确认入库。
7. 仓管不能自行生效需老板确认的纠错；批准后库存、成本及已审核提成一致更新，失败不留部分结果。
8. 普通新采购不改变已固定历史订单成本。
9. 数量纠错导致负库存时拒绝生效、提示核对，原库存及成本保持不变；老板确认不能绕过此校验。

## 待确认边界

- 占货修改模式中订单数量、客户预留及其他锁定的调整细节。
- 破损采购退款的具体成本扣减方法，包括未退还采购运费的处理。
- 金额精度、舍入、异常大值提醒阈值、业务影响判断及重算时间顺序。

以上未定事项不妨碍保存已确认规则，但实施相应行为前必须明确，不据此自行添加功能。
