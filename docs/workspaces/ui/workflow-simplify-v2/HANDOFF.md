## 三页交互合同

| 页面 | 必须保留的行为 |
| --- | --- |
| 新建订单 | 同页“客户与交付→添加商品→核对订单”；当前展开并突出主操作，已完成摘要可修改、待完成弱化。客户与商品可独立编辑，允许先选品，只在核对确缺真实前提时阻止继续。 |
| 商品区 | 多SKU连续搜索添加、每行独立选择仓库/数量/价格并可移除，避免每个SKU再走向导；显示所选仓SKU可售量及当前成本参考/单位。切换阶段、返回修改和失败不清空其它输入。不得代猜成交价或仓库。 |
| 核对与详情 | 同页核对后明确确认，手机底栏显示合计及返回/确认。成功进入同一真实订单，保持现有上传付款凭证、出库/现场交付、收货及核对入口与权限；不得把“保存成功”伪装为收款或出库成功。 |
| 采购入库 | 同页“仓库与供应商→录入实收→核对入库”；非默认运费/预留/破损/提醒设置折叠后有简短摘要。核对展示真实服务结果，成功替换表单，避免继续重复确认同单。原型不授权同单新增圈货能力。 |

- 新客户、散客、地址、开票及其它真实业务字段继续已有规则；现场交付隐藏不适用收货地址。少文案不删除必要错误及暂停原因。
- 当前阶段用边框、数字、状态标记和主按钮共同强调；不能只靠颜色。完成摘要的修改入口清晰可见。
- 字段旁错误配合可聚焦的错误摘要；跨阶段错误可展开对应区并聚焦字段。展开阶段不强制弹出选择器或手机键盘。
- 异步加载、服务端失败、重复提交防护、幂等和丢响应恢复复用真实应用，不复制原型同步演示状态。

## 排版、动效与响应式

- 正文16px为本轮基准，单行控件42px、主要操作至少44px；原型手机确认实测46px。遵循已批密度，输入宽度按内容分配，充分使用横向空间，不添加大块无效留白。
- 内容区右侧文字水平左对齐，金额/数量可在行右端独立对齐；不要恢复旧居中文字。大金额、长SKU/客户名、错误文字不可硬裁；窄屏合理换行/独立区域，页面根不横溢。
- 步骤淡入轻位移200ms、新增行反馈220ms；原生CSS即可。系统减弱动态时关闭动画、过渡及平滑滚动。动效不应阻塞输入或确认。
- 桌面与手机均保留清晰阶段定位；手机底栏不得遮挡最后字段、错误、金额或确认操作。保留键盘焦点样式及搜索选择器键盘操作。

## 真实成本接口接入边界

公共业务依据为[成本与提成调整](../../../project/COST_COMMISSION_REVISION_20261019.md)，实现以固定后端及API为准，不从原型JS推导金额。

- 新口径未出库成本、毛利、提成及行成本可为null；保留“未出库/未核算”语义，不能转0、直接插入字符串null或据此算利润。旧记录仍按服务返回的旧口径展示。
- 行 `current_unit_cost_reference` 是当前仓SKU成本参考，三位小数字符串；切换仓/SKU后取真实最新值，只读、明确参考性质，不表示已锁定出库成本。未知值不能当零。
- 未实际出库不提前显示毛利/提成；实际出库后使用服务返回的实际成本及计算结果，正式提成资格继续原完成、收款核对与复核条件。不能以展示均价乘回数量代替最终实际成本。
- 负责人另授权 `order_form/detail/report/adjustments` 必要空金额呈现适配；报表和调整页只做兼容，不借此重设计。
- 老板独立提成差额确认API不是本三页设计：`POST /api/v1/orders/{order_id}/commission-adjustment-confirm` 无尾斜杠，成功直接返回操作结果而非统一包裹。权限与版本条件沿后端；若接现有控件，先向负责人提出最小方案，不新增未经批准页面，也不把差额确认显示为已转账。
